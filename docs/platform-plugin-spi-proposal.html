Atlas 平台化架构：现状全景 + 演进方案

② 平台单向 SPI：现状（已落地）

平台核心功能不仅是「被动被插件调用」，而是主动向插件开放三类 SPI：能力门面、事件订阅、声明式接入。契约定义在 packages/types/src/index.ts，运行时在 SpiModule（@Global）+ PlatformPluginEnvironment。

1能力门面（插件 → 主动调平台）

门面能力
env.apps()应用空间读取 / 创建：list / get / create
env.monitor()数据面聚合读取 + registerMetric 自定义指标（绑定调用方 appId）
env.security()公开前缀注册 + IP 黑名单管理
env.platform()平台版本 / 安全子集配置 / 元信息

2事件订阅（平台 → 被动通知插件）

基于 @nestjs/event-emitter 的类型化事件总线，核心服务生命周期变更时 emit，插件用 env.events().on() 订阅，实例销毁自动退订。

应用事件

app.created / updated / activated / revoked / deleted / secret.rotated

数据集事件

dataset.created / updated / published / deleted

插件事件

plugin.loaded / unloaded / enabled / disabled / deleted

3声明式接入（AtlasPlugin 钩子）

钩子职责
schemaDdl()启动幂等建表（CREATE TABLE IF NOT EXISTS，失败隔离）
cleanupTables()应用删除时同事务级联清理插件表
logTables()声明插件日志表，纳入 LogCleanupService 定时清理
publicUrls()注册公开 URL 前缀，SecurityMiddleware 放行
resourceName()监控聚合的插件资源类型显示名解析
关键点：这是「平台 → 插件」的单向 SPI，已实现且有全套文档。插件之间目前无直接调用，靠「数据集 + GLOBAL_SHARED store」协作——这正是下一步要补的方向。
提案

③ 插件双向 SPI：可行，且推荐 未实现 · 提案

「插件本身暴露 SPI 供平台内核与其他插件交互」——完全可行，是插件平台的标准演进方向（类似 Home Assistant 的 integration、WordPress filter/action、LSP 的 capabilities）。在已实现的单向 SPI 之上，补齐反向：插件→插件、插件→内核。

回答你的问题：可以。设计上让插件用 provides() 声明自己暴露哪些「能力命名空间」，其他插件用 env.spi() 消费，平台内核用 PluginSpiRegistry 消费；配合 dependsOn 声明依赖、拓扑排序、作用域校验、null 降级。

1插件 SPI 契约（packages/types）

// 插件暴露一个 SPI 能力
export interface PluginSpiExport {
  describe: string
  create(env: PluginEnvironment): unknown   // 用提供方自己的 env 构建
}
export interface PluginSpiDependency { pluginType: string; spi?: string }

// AtlasPlugin 新增两个可选钩子
provides?:  () => Record<string, PluginSpiExport>   // namespace → 能力工厂
dependsOn?: () => PluginSpiDependency[]             // 依赖声明

// PluginEnvironment 新增消费方法
spi<T = unknown>(pluginType: string, namespace: string, targetAppId?: number): T | null

🔌 消费方示例 · 另一插件调用

// 在 endpoint / handler 调用期求值（免疫 init 顺序）
handle: async (env) => {
  const gw = env.spi<ModelGatewaySpi>('providers', 'model-gateway')
  if (!gw) return { ok: false, reason: '能力不可用' }  // 降级
  return await gw.complete({ providerId, messages })
}

2类型化方案：双轨

一等能力 · 名义类型安全

扩展 @atlas/types（新增 types/src/spi/*）定义接口，提供方 create 返回该类型，消费方 env.spi<ModelGatewaySpi>(...)。运行时无跨插件 import（插件是动态 import 隔离的），仅类型在编译期共享。

第三方能力 · 鸭子类型

消费方本地声明接口 + env.spi<LocalShape>(...)。spi() 泛型默认 unknown，不强转即得安全默认。

3运行时注册中心（新文件）

方法职责
register(pluginType, appId, scope, exports, buildEnv)构建并缓存 SPI 对象，key = ${pluginType}@scopeKey
unregister(pluginType, appId?)注销；不带 appId 清该类型全部实例
resolve(pluginType, namespace, consumerAppId)解析；不可用一律返回 null
namespacesOf(pluginType)管理面展示某插件暴露的命名空间

不依赖 PluginService（避免反向循环），由 PluginService 编排驱动。平台内核通过新的 PLUGIN_SPI_REGISTRY Symbol token 注入消费——沿用现有门面模式（tokens.ts）。

4生命周期接入（编排权在 PluginService）

启用

enableInstance 构建 env 后，若 provides()` 非空则 register，SPI 即就绪。

注销

deleteInstance / unload / 热替换时 unregister；订阅 loaded/unloaded 事件统一定清/重建。

依赖拓扑

autoInstantiate 内对 dependsOn 拓扑排序（先启用被依赖方）+ 环检测，发现环拒启并告警。

5作用域与降级

提供方 scope可被谁解析
GLOBAL_SHARED任意 consumerAppId（数据本就共享），缓存于 @0
APP_LOCAL仅当 consumerAppId === 提供方 appId
未加载 / 未暴露 / 未启用一律 null，消费方回退
安全红线：SPI 是进程内、受信集群代码调用。严禁新增 /spi/:type/:ns HTTP 透传路由，只允许经插件自身声明的端点暴露；跨插件调用走 ops() 审计。

6设计取舍

与现有协作互补

默认仍鼓励「数据集 + GLOBAL_SHARED store」松耦合协作；SPI 留给操作型能力（网关 / 推理 / 嵌入）。两模式各司其职。

前端维持 HTTP runtime

不新增浏览器内 SPI 总线。前端插件是 ui/ 静态包，经同一端点 / 数据集消费即可，避免与后端 SPI 重复。

提案

④ 插件业务表迁移 未实现 · 提案

把 6 张插件表从 core 迁出，让 core schema 只含真正的平台基础表，插件彻底自治。用户已确认迁移方向。

1 · 插件加 schemaDdl

providers / prompts / model-files 各在 src/index.ts 加 schemaDdl: () => [CREATE TABLE IF NOT EXISTS …]（从 core schema 对应 DDL 复制，含索引）。

2 · core 删除

core/src/db/schema.sql 删除这 6 张表的 CREATE。LEGACY_TABLES 保留（dev-reset 仍清，插件幂等重建）。

平滑迁移：插件 schemaDdl 是 CREATE TABLE IF NOT EXISTS，由 SchemaBootstrapService 在 core schema 之后执行 → 旧库已有表不重建、不丢数据，无需数据迁移。
